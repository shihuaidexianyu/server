# 服务器管理

本章主线：按原部署接口记录完成账户生命周期管理，并在执行前核对部署版本、授权和数据交接。原记录称 `userkit` 为 Linux 账户管理 CLI、版本 `0.1.0`，可开户、公钥/密码管理、sudo 授权和删除用户。

**适用版本：**以下是 `userkit 0.1.0` 的历史接口记录。实际命令、输出、权限和安全机制须按部署版本的源码及 `--help` 确认，不能仅凭这份接口记录作出实现或安全保证；即使使用 `--dry-run`，启动阶段也可能准备依赖或写缓存。

> **【警告】管理员专用**
>
> - **适用对象**：拥有服务器账户管理职责的管理员。
> - **前置条件**：确认 `userkit` 的实际部署路径，并保留另一个可用管理员账户或 BMC 恢复方式。
> - **所需权限**：原接口称查询和账户计划可用普通权限，真实修改需管理员权限；仍须核对启动脚本是否会安装依赖或写缓存。
> - **完成标准**：先通过 `--dry-run` 审核计划，执行后用 `userkit show` 和实际 SSH 登录验证结果。

常见任务入口：

| 任务 | 在页面目录中查找 |
| --- | --- |
| 新增用户 | “新增用户” |
| 更新 SSH 公钥 | “SSH public key 管理” |
| 授予或撤销 sudo | “授予 sudo”“撤销 sudo” |
| 删除用户 | “删除用户” |
| 标准操作顺序 | “推荐工作流” |
| 排查失败 | “常见问题” |

## 工具位置和启动方式

原记录称 `userkit` 部署在管理员主目录下，路径形式通常为 `/home/<admin_name>/userkit`。实际服务器路径以部署位置为准。

日常使用时，`userkit` 一般通过项目根目录下的 Bash 脚本启动，也就是直接执行：

```bash
./userkit
```

或者在需要真实修改系统账户时执行：

```bash
sudo ./userkit
```

也就是说，管理员通常不需要手动执行 `python -m userkit`，也不需要依赖已经安装到全局 PATH 的 `userkit` 命令。原记录称 Python、uv、虚拟环境由启动脚本处理；这些入口本身也是执行代码，必须先核查所有权、权限和来源。

常见使用方式是先进入项目目录：

```bash
cd /home/<admin_name>/userkit
```

查看帮助：

```bash
./userkit --help
```

进入交互模式：

```bash
./userkit
```

以管理员权限执行真实修改：

```bash
sudo ./userkit
```

该历史接口记录中的启动脚本查找顺序为：

1. 如果存在 `.venv/bin/python`，使用该 Python 执行 `python -m userkit`。
2. 否则寻找 `/usr/local/bin/uv`、`/usr/bin/uv`、`/bin/uv`，使用 `uv run --project` 执行。
3. 否则使用系统 `python3`，并临时设置 `PYTHONPATH=项目目录/src`。

启动脚本会把 `PATH` 限定为：

```text
/usr/sbin:/usr/bin:/sbin:/bin
```

并清理 `PYTHONPATH`、`PYTHONHOME`。即使这些措施确实存在，也不等于代码可信：使用 sudo 执行用户可写的脚本、虚拟环境或 Python 模块，仍会以 root 执行其中的代码；`uv run` 也可能解析/安装依赖。部署审查应覆盖入口、解释器、模块和依赖，不能只检查 PATH。

## 权限模型

`show` 查询类操作不需要 root。

会修改系统账户的操作必须满足下面二者之一：

- 使用 `sudo` 以 root 身份运行。
- 加上 `--dry-run`，只打印计划，不做真实修改。

例如：

```bash
./userkit add <username> --public-key '<ssh_public_key>' --dry-run
```

按原接口设计，这应展示账户计划而不创建用户；未核实源码前不要推定启动和依赖准备也完全无副作用。

交互模式下，如果不是 root，`userkit` 会展示操作摘要和 dry-run 计划，然后停止，不会修改系统。

## 子命令总览

| 子命令 | 作用 | 是否修改系统 |
| --- | --- | --- |
| `interactive` / `menu` / `wizard` | 启动交互菜单 | 取决于选择的操作 |
| `show` | 列出用户或查看单个用户 | 否 |
| `add` | 创建用户 | 是 |
| `set-key` | 替换或追加 SSH public key | 是 |
| `passwd` | 交互式设置账户密码 | 是 |
| `grant-sudo` | 写入 userkit 管理的 sudoers 规则 | 是 |
| `revoke-sudo` | 删除 userkit 管理的 sudoers 规则 | 是 |
| `delete` | 删除用户 | 是 |

通用安全选项：

| 选项 | 作用 |
| --- | --- |
| `--dry-run` | 只打印计划，不修改系统 |
| `--allow-current-admin` | 允许修改当前 sudo 调用用户 |
| `--allow-system-user` | 允许修改 UID 小于 1000 的系统用户 |

`--allow-current-admin` 和 `--allow-system-user` 只应在确认有其它管理员恢复路径时使用。

## 查看用户

列出符合原工具筛选条件的账户：

```bash
./userkit show
```

查看单个用户：

```bash
./userkit show <username>
```

输出 JSON：

```bash
./userkit show --json
./userkit show <username> --json
```

该接口记录中的交互用户候选筛选规则为：

- UID 必须大于或等于 `1000`。
- 用户名不能是受保护系统用户。
- 用户名不能以 `systemd-` 开头。
- shell 不能是 `false`、`nologin`、`sync`、`shutdown`、`halt`。

列表模式会显示：

```text
USER  UID  PERMISSION  PRIMARY  GROUPS  SSH_KEYS  SHELL
```

单用户模式会显示：

- 用户名。
- UID/GID。
- 主组。
- home 目录。
- shell。
- 所属组。
- sudo 权限来源。
- `authorized_keys` 路径。
- SSH key 数量和 SHA256 指纹。

原接口列出的 sudo 来源标签分为两类：

- `userkit`：存在 `/etc/sudoers.d/userkit-<username>`。
- `group:sudo`、`group:wheel`、`group:admin`：用户属于这些 sudo 相关用户组。

这些标签只提供配置线索：组成员或文件存在不保证有效授权，也不覆盖 LDAP、其它 sudoers 规则等全部来源。管理员应检查有效 sudo 策略（例如 `sudo -l -U <username>`），不能以“show 没标 sudo”推定权限已撤销。

## 新增用户

新增用户必须至少提供一种登录方式：

- `--public-key`：写入 SSH public key。
- `--ask-password`：交互式设置初始密码。

推荐使用 SSH public key：

```bash
sudo ./userkit add <username> --public-key '<ssh_public_key>'
```

先查看计划：

```bash
./userkit add <username> --public-key '<ssh_public_key>' --dry-run
```

设置登录 shell：

```bash
sudo ./userkit add <username> \
  --public-key '<ssh_public_key>' \
  --shell /bin/bash
```

加入已有附加组：

```bash
sudo ./userkit add <username> \
  --public-key '<ssh_public_key>' \
  --groups <group_name_1>,<group_name_2>
```

同时授予 sudo：

```bash
sudo ./userkit add <username> \
  --public-key '<ssh_public_key>' \
  --sudo
```

授予免密码 sudo：

```bash
sudo ./userkit add <username> \
  --public-key '<ssh_public_key>' \
  --sudo \
  --passwordless-sudo
```

新增用户实际执行的核心系统命令包括：

```bash
useradd --create-home --shell /bin/bash <username>
usermod -aG <group_name_1>,<group_name_2> <username>
```

该接口记录以 `chpasswd` 写入密码。注意：禁用 SSH 密码登录不妨碍本地密码用于 sudo/PAM；仅公钥开户且账户无可用密码时，随后授予“需密码 sudo”未必能正常使用，应检查账户认证策略，而非默认改免密。

## 用户名和组名规则

原记录的 userkit 输入限制为（不是所有 Linux 发行版通用命名规则）：

- 只能包含小写字母、数字、下划线 `_`、短横线 `-`。
- 必须以小写字母或 `_` 开头。
- 最多 32 个字符。
- 不能是受保护系统用户。
- 不能以 `systemd-` 开头。

合法示例：

```text
alice
alice_1
lab-user
```

非法示例：

```text
Alice
1alice
alice.name
```

原记录要求附加组满足类似命名规则且已存在。`userkit` 不会自动创建不存在的组。

受保护用户包括 `root`、`daemon`、`bin`、`sys`、`sync`、`www-data`、`backup`、`_apt`、`nobody` 等系统账户。

## SSH public key 管理

设置 SSH public key：

```bash
sudo ./userkit set-key <username> --public-key '<ssh_public_key>'
```

默认行为是替换用户的 `authorized_keys`。

如果要追加而不是替换：

```bash
sudo ./userkit set-key <username> \
  --public-key '<ssh_public_key>' \
  --append
```

支持的 key 类型：

- `ssh-ed25519`
- `ssh-rsa`
- `ecdsa-sha2-nistp256`
- `ecdsa-sha2-nistp384`
- `ecdsa-sha2-nistp521`

原记录不支持 `ssh-dss`，并检查 base64 key blob。`ssh-rsa` 公钥类型和已弃用的 SHA-1 `ssh-rsa` 签名算法不是同一概念；RSA 公钥能否登录取决于客户端/服务器支持的签名及策略，不应为了兼容旧工具重新启用 SHA-1。

该接口记录中的写 key 检查如下；部署时需确认其实现及并发、失败处理：

- home 目录必须存在。
- home 目录必须属于目标用户。
- home 目录不能被 group 或 others 写入。
- 不跟随 `.ssh` 或 `authorized_keys` 的符号链接。
- `.ssh` 权限会设置为 `700`。
- `authorized_keys` 权限会设置为 `600`。
- 文件所有者会设置为目标用户。
- 修改已有 `authorized_keys` 前会备份。

SSH 登录说明参见 [SSH 登录](ssh登录.md)。

## 设置密码

为用户设置密码：

```bash
sudo ./userkit passwd <username>
```

命令会交互式输入两次密码。密码不能为空，不能包含换行符，两次输入必须一致。

如果服务器禁用了 SSH 密码登录，这个密码通常只用于本地认证、sudo 或其它系统认证场景，不代表可以通过 SSH 密码登录。

## 授予 sudo

授予需要密码的 sudo：

```bash
sudo ./userkit grant-sudo <username>
```

授予免密码 sudo：

```bash
sudo ./userkit grant-sudo <username> --passwordless
```

`userkit` 不通过把用户加入 `sudo` 组来管理这类权限，而是写入：

```text
/etc/sudoers.d/userkit-<username>
```

需要密码的 sudoers 内容形如：

```sudoers
# Managed by userkit. Do not edit this file by hand.
<username> ALL=(ALL:ALL) ALL
```

免密码 sudoers 内容形如：

```sudoers
# Managed by userkit. Do not edit this file by hand.
<username> ALL=(ALL:ALL) NOPASSWD: ALL
```

写入前会使用 `visudo -cf` 检查临时文件，写入后会执行 `visudo -c` 检查全局 sudoers 配置。文件权限会设置为 `0440`，所有者为 `root:root`。

## 撤销 sudo

撤销 userkit 管理的 sudo：

```bash
sudo ./userkit revoke-sudo <username>
```

这只会删除：

```text
/etc/sudoers.d/userkit-<username>
```

按原记录，它不移除组授权；这些组是否被 sudoers 赋权取决于本机策略。其它文件、目录服务或集中授权也可能继续生效，撤销后须核对有效授权，而不是只检查这一份文件。

## 删除用户

删除用户但保留 home：

```bash
sudo ./userkit delete <username>
```

删除用户并删除 home：

```bash
sudo ./userkit delete <username> --remove-home
```

删除前备份 home：

```bash
sudo ./userkit delete <username> --remove-home --backup-home
```

如果启用 `--backup-home`，备份会写入：

```text
/var/backups/userkit/<username>-home-<timestamp>.tar.gz
```

删除用户时，`userkit` 会先撤销 userkit 管理的 sudoers 文件，然后执行：

```bash
userdel <username>
```

如果带 `--remove-home`，实际会执行：

```bash
userdel --remove <username>
```

`userdel --remove` 通常处理 home 和 mail spool，不能据此推定 `/data` 等其它文件系统上的数据一并删除；原记录的 home 备份也未承诺包含 `/data`、ACL/xattr 或所有挂载内容。备份应校验清单并做恢复检查。删除账户后遗留文件仍按数字 UID/GID 归属，后续复用 UID 可能让新账户取得旧数据。

删除用户前必须确认：

- 用户没有正在运行的重要任务。
- `/home/<username>` 和 `/data` 中的数据已经处理。
- 需要保留的数据已经备份或转交。
- 该用户不是当前唯一管理员路径。

## 交互模式

以下命令都会进入交互菜单：

```bash
./userkit
./userkit interactive
./userkit menu
./userkit wizard
```

交互模式包含：

1. 新增用户。
2. 列出真实用户。
3. 设置 SSH public key。
4. 设置密码。
5. 授予 sudo。
6. 撤销 userkit 管理的 sudo。
7. 删除用户。

如果终端支持 TUI，会使用上下键选择；否则使用数字或快捷键。任意输入处可以输入：

```text
q
quit
exit
cancel
back
```

取消当前操作。

交互模式执行真实修改前会：

1. 打印操作摘要。
2. 先跑 dry-run 计划。
3. 如果当前不是 root，只展示计划并停止。
4. 如果当前是 root，要求输入精确确认短语。

确认短语示例：

| 操作 | 确认短语 |
| --- | --- |
| 新增用户 | `add alice` |
| 替换 key | `replace-key alice` |
| 追加 key | `append-key alice` |
| 设置密码 | `passwd alice` |
| 授予 sudo | `grant-sudo alice` |
| 撤销 sudo | `revoke-sudo alice` |
| 删除用户 | `delete alice` |

## 安全保护机制

下列安全机制属于该接口的设计约定；使用前须确认部署实现是否具备：

- 修改系统账户时要求 root。
- `--dry-run` 不执行真实修改。
- 默认保护当前 sudo 调用用户，避免管理员把自己降权或删除。
- 默认拒绝管理 UID 小于 1000 的系统用户。
- 使用 `/run/userkit/accounts.lock` 做账户修改锁，避免并发修改。
- 只从可信系统路径解析 `useradd`、`usermod`、`userdel`、`chpasswd`、`tar`、`visudo` 等命令。
- 拒绝执行带路径分隔符的命令名。
- 拒绝执行非 root 拥有、可被 group/others 写入、非普通文件或不可执行的系统命令。
- 子进程环境只保留可信 `PATH`。
- sudoers 文件采用临时文件、`visudo` 校验、备份、原子替换。
- SSH key 写入时拒绝跟随符号链接。

备份目录为：

```text
/var/backups/userkit
```

该目录会以 `0700` 权限创建。

## 推荐工作流

新增用户建议流程：

1. 收集用户名和 SSH public key。
2. 先核对可信部署源码/版本、启动依赖和子命令帮助，再用 `./userkit add ... --dry-run` 检查账户计划。
3. 用 `sudo ./userkit add ...` 执行。
4. 用 `./userkit show <username>` 检查 UID、组、shell、SSH key 和 sudo 权限。
5. 让用户从本机测试 SSH 登录。

修改 SSH key 建议流程：

1. 先确认是替换还是追加。
2. 替换前提醒用户旧 key 会失效。
3. 使用 `sudo ./userkit set-key ...`。
4. 使用 `./userkit show <username>` 核对 key 指纹。

删除用户建议流程：

1. 确认用户已离组或不再需要账户。
2. 检查是否有运行中的进程。
3. 检查 `/home/<username>` 和 `/data` 下的数据。
4. 如需备份 home，使用 `--backup-home`。
5. 如需同时删除 home，使用 `--remove-home`。
6. 删除后检查账户、有效授权、个人服务/计划任务/凭据及 home、/data 的数字 UID 遗留；本工具接口不证明这些都已处理。

## 常见问题

### 普通用户运行 add/delete 报错

修改账户必须 root。先使用 `--dry-run` 看计划，确认后再：

```bash
sudo ./userkit <subcommand> ...
```

### revoke-sudo 后用户仍能 sudo

可能是组授权、其它 sudoers 文件或集中策略。原记录称 revoke-sudo 只删除自身管理文件；由管理员核对 `sudo -l -U <username>` 的有效策略和其它来源。

### set-key 失败，提示 home 权限问题

`userkit` 要求 home 目录属于目标用户，并且不能被 group 或 others 写入。检查：

```bash
ls -ld /home/<username>
```

常见修复：

```bash
sudo chown <username>:<username> /home/<username>
sudo chmod 700 /home/<username>
```

### 附加组不存在

`--groups` 只接受已经存在的组。先检查：

```bash
getent group <group_name>
```

如果需要新建组，应由管理员单独创建并确认用途。

### 想修改当前管理员账户

默认会保护当前 sudo 调用用户。只有在已经确认有其它可用管理员账户、BMC 或恢复方式时，才考虑使用：

```bash
--allow-current-admin
```

### 想管理系统用户

默认拒绝 UID 小于 1000 的系统用户。除非明确知道后果，不要使用：

```bash
--allow-system-user
```

通用账户与授权机制可参考 [Ubuntu sudo 手册](https://manpages.ubuntu.com/manpages/jammy/man8/sudo.8.html)、[Ubuntu userdel 手册](https://manpages.ubuntu.com/manpages/jammy/man8/userdel.8.html)、[sudoers](https://www.sudo.ws/docs/man/sudoers.man/) 和 [visudo](https://www.sudo.ws/docs/man/visudo.man/)；RSA 密钥与 SHA-1 签名的区别见 [OpenSSH 8.8 发布说明](https://www.openssh.org/txt/release-8.8)。这些通用手册不能替代部署版 `userkit` 的实现说明。
