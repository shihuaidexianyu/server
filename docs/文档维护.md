# 文档维护规范

> **【说明】适用对象与目标**
>
> - **适用对象**：服务器管理员和文档维护者。
> - **目标**：确保公开文档可执行、可验证，并且不泄露基础设施和账户信息。


## 维护责任

文档由“实验室服务器管理员”这一角色维护。具体负责人和联系渠道属于内部交接信息，不在公开站点记录。

每次修改服务器环境后，应同步检查对应文档；不能确认的信息应明确写成“待验证”，不要把示例路径写成当前事实。

## 公开与私有信息边界

以下信息不得进入公开仓库、提交历史、Actions 构建产物或聊天记录：

- 真实服务器 IP、主机名和 SSH 指纹。
- BMC IP、访问地址、账号和密码。
- 网络认证账号、代理主机地址、订阅和 token。
- 管理员个人联系方式和未公开账户。
- SSH 私钥、API key、密码和其它凭据。

优先使用受控密码管理工具；需要本地私有文件时放在 `.local-private/` 并限制访问。`.gitignore` 只防止新文件被意外跟踪，不能移除已跟踪文件、历史泄露或备份副本；不要仅凭忽略规则判定安全。

## 页面基本结构

面向操作的页面应尽量按以下顺序编写：

1. 适用对象。
2. 前置条件和所需权限。
3. 完成标准。
4. 最短操作步骤。
5. 预期输出或成功现象。
6. 常见失败和恢复方法。
7. 安全边界与升级渠道。

命令中的变量统一使用 `<username>`、`<server_alias>`、`<path>` 等占位符。示例名称必须明显是虚构值。

## 需要定期验证的内容

| 内容 | 建议负责人 | 触发条件 | 验证方式 |
| --- | --- | --- | --- |
| SSH 与账户流程 | 账户管理员 | SSH 或 userkit 配置变化 | 新测试账户完成一次登录 |
| `/data` 权限 | 存储管理员 | 挂载或用户组变化 | 普通用户创建并删除测试文件 |
| 公共软件 | 软件维护者 | 安装、升级或环境变量变化 | 运行版本和最小功能测试 |
| 普通网络与代理 | 网络维护者 | 认证或代理配置变化 | 分别测试直连和代理访问 |
| 防火墙与 BMC | 系统管理员 | 规则、固件或地址变化 | 按管理员检查表验证 |
| 文档构建 | 文档维护者 | 每次文档提交 | 在本站目录、已准备依赖的环境中执行 `mkdocs build --strict` |

## 推荐审阅周期

- 服务器配置变化后立即审阅相关页面。
- 公共软件升级后记录版本和验证日期。
- 至少每季度走一遍 [15 分钟快速开始](快速开始.md)。
- 离组、管理员变更或网络调整后更新私有交接信息。

## 发布检查

提交前至少完成：

```bash
../.venv/bin/python -m mkdocs build --strict
```

该命令从 `服务器/` 执行，使用 qhwiki 根现有虚拟环境；若缺少依赖，由维护者按 README 准备。默认构建会清理 `site/`，需要保留旧产物或做隔离验证时用 `--site-dir <isolated_site_dir>`。`--strict` 把构建警告当作失败，不核验服务器配置、命令正确性或信息泄露。

同时检查本次差异与已跟踪文件，确认私有信息没有进入源码、历史或产物。本站本地 workflow 配置为 push `main` 或手动触发后构建，再由 GitHub Pages 发布；远端还需启用 Pages 的 GitHub Actions 来源和所需权限。本地构建成功不等于上线成功，发布状态须查看远端运行结果。

参考：[MkDocs CLI](https://www.mkdocs.org/user-guide/cli/) 和 [GitHub Pages 发布来源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。
